# Storefront API 与询盘管理设计基线

**状态：** 待用户审阅  
**日期：** 2026-10-12  
**选定模板：** `template_id: gas-grill`  
**交付范围：** gas-grill 店铺的商品/分类/公司内容 API 化、询盘收集与轻量跟进管理。继续扩展现有模板，不新建模板。

## 目标

将当前 Next.js 静态 mock 展示站逐步演进为每店独立部署的展示型外贸 storefront：展示内容由该店自己的 Go API 和 PostgreSQL 提供；公开询盘可被可靠持久化，并由少量内部用户进行基础跟进。首期不实现购物车、结账、支付、跨店铺 CRM、多租户共享数据库或完整销售自动化平台。

## 当前项目基线

- Storefront 使用 Next.js 15 / React 19，模板标识为 `gas-grill`。
- 商品与分类目前位于 `src/lib/catalog/mock-data.ts`；公司内容模板已存在。
- 管理端商品数据目前使用浏览器 `localStorage`，不是共享或生产级后台。
- 仓库 README 当前明确没有 Go API 或数据库；Go API 与每店独立 PostgreSQL 属于规划能力。
- 现有页面包括首页、分类页、商品详情页与公司内容页面。

## 架构决策

1. **每店一个独立部署边界。** 每个店铺运行自己的 Go API 与 PostgreSQL，内容和询盘只属于该店；首期不设计跨店查询或共享 CRM。
2. **Go API 与数据库作为店铺内容的来源。** 商品、分类、公司展示内容和种子/mock 内容最终由该店 API 提供。Next.js 保持展示与页面组合职责，不在模板组件中绑定数据库实现。
3. **保持模板边界。** `template_id: gas-grill` 的页面 composition 继续归属 `src/components/templates/gas-grill/` 与 `src/app/`；共享 catalog/content 契约位于 `src/lib/catalog/`；模板注册信息继续归属 `src/lib/templates/registry.ts`。
4. **轻量自建询盘管理优先。** 不先引入完整 CRM。开源 Go CRM 可作为参考/备选，正式采用前需单独检查维护活跃度、许可证、迁移能力、安全性、表单适配及部署成本。
5. **核心字段与扩展字段并存。** 状态、提交时间、产品关联、来源、联系人邮箱等稳定且需要筛选/校验/报表的字段使用明确结构；尚未稳定的运营字段可配置定义与类型，不把所有数据无差别塞入 JSON。
6. **管理端最小权限。** 初期服务单店的一人或少量用户，先满足安全登录和基本管理，不实现复杂角色、审批、团队路由或跨店权限。

## 内容和真实性约束

- 展示内容应明确区分有依据、可验证的公司/产品事实与样板占位内容。
- 不得把未验证的认证、测试结果、产能、交期、MOQ 或品质承诺写成事实。
- 数据契约要 API 友好，模板组件消费内容合同，不直接依赖数据库或 ORM。
- 保留当前 `gas-grill` 模板视觉与内容一致性；不通过 visitor-facing 模板切换引入第二套风格。

## 询盘流程与字段基线

### 网站访客提交字段

必填项应尽量精简，以保证询盘可联系且意图可识别；除联系邮箱和必要的隐私同意外，字段是否强制应在实施设计中再结合表单体验确认。

- 联系人姓名
- 联系邮箱
- 公司名称（可选）
- 电话/WhatsApp（可选）
- 目的国家/地区
- 感兴趣产品：产品 ID 及提交时产品型号/名称快照
- 预计数量（可选）
- 定制需求/留言
- 附件（首期可独立排期）
- 隐私说明及同意记录
- 来源页面/产品页、提交时间

商品详情页进入询盘表单时应预填产品及型号。询盘保存的产品名称和型号快照不应因后续商品编辑而改变。

### 店铺运营字段

- 状态：`new`（新询盘）、`in_progress`（跟进中）、`quoted`（已报价）、`won`（成交）、`lost`（未成交）、`on_hold`（暂缓）。访客表单不可设置这些字段。
- 负责人：初期可选或默认店铺管理员。
- 最近联系时间。
- 下一步跟进动作与日期。
- 跟进备注/活动记录。
- 未成交原因：可选；先支持记录，后续根据实际情况归纳枚举。

状态和活动历史分开保存。至少需要记录活动发生时间；管理操作应能区分创建、备注/联系、状态变化等事件。

### 数据职责建议

- **Inquiry**：访客提交主体、产品快照、来源、隐私同意及运营状态/时间戳。
- **Inquiry activity**：备注、联系记录、状态变化和跟进行动历史。
- **Field definition/value**：未来可配置的运营扩展字段；仅在具体需求明确后实现，不阻塞稳定核心模型。
- **Attachment metadata**：原始文件名、媒体类型、大小、存储标识/位置及关联询盘。文件采用受控文件存储，不将二进制内容放入 PostgreSQL。

## 交付分解（Issue 候选）

Issue 按可独立验收的交付拆分；确切顺序、依赖与范围应在用户确认本文后细化。

1. **数据/API 契约与实现边界**：商品、分类、公司内容、询盘、状态和活动模型；API 错误、版本与配置约定；明确展示事实和占位数据的表达方式。
2. **Go + PostgreSQL 项目骨架**：服务启动、配置、数据库连接、迁移、健康检查、测试基线和本地开发编排；每店独立部署。
3. **数据库 mock/seed 内容与 catalog API**：种子商品/分类/公司内容可通过 API 查询；数据字段满足当前 gas-grill 展示需求。
4. **Next.js catalog API 接入**：首页、分类、详情、公司页面读取 API；定义 API 不可用、未知 slug、空集合等行为；更新 README 的实际启动说明。
5. **询盘持久化 API**：输入校验、产品快照、来源记录、隐私同意、基础速率/反垃圾保护和安全错误响应；不信任客户端提交的运营状态字段。
6. **Storefront 询盘表单**：全站与详情页 CTA、产品预填、表单校验、提交中/成功/失败状态、隐私说明；附件可后续独立交付。
7. **轻量管理端**：安全登录、询盘列表/详情、状态更新、备注/活动、下一步跟进；适配少量内部用户。
8. **后续按需扩展**：附件存储、自定义运营字段、导入导出和更深入的统计；基于实际使用证据决定优先级。

## 非目标

- 购物车、订单、结账、支付或第三方电商插件。
- 共用数据库中的多店租户系统或集中查看多店询盘的公共 CRM。
- 在字段尚未通过真实业务验证前实现全功能通用对象/字段平台。
- 首期实现自动评分、复杂 BANT/MEDDIC、销售邮件序列、营销自动化或复杂团队分配。
- 未经证据支持的公司实力、产品参数和交期承诺。

## 安全、隐私与可靠性要求

- 公开询盘入口需服务端校验、限流/反垃圾措施和安全错误处理。
- 管理端必须有认证保护；不能把 localStorage 或前端隐藏路由当作访问控制。
- 对个人联系方式最小化收集，并明确说明用途；保存隐私同意记录。
- 附件若实施，限制大小和允许类型，避免可执行内容被公开访问，并使用独立文件存储。
- 生产运行需要可配置密钥、数据库备份/恢复说明和迁移策略；具体实现写入对应阶段计划。

## 验收方向

- 每个店铺的数据和运行边界相互独立。
- 商品、分类、公司内容通过 API/数据库提供，前端模板只依赖稳定内容契约。
- 访客询盘经 API 写入数据库，产品信息快照与来源可追溯。
- 管理员可安全查看和更新询盘状态、追加活动并安排下一步跟进。
- 错误、空数据、未知产品/路由、移动端与键盘可访问性纳入相关阶段检查。
- README 与实际能力一致；不把 mock 种子数据、localStorage 或演示部署描述成生产级能力。
- 遵循仓库 `AGENTS.md` 与 `TESTING.md` 中的模板、测试和交付约定。

## 待实施阶段确认的决策

以下事项不阻塞总体方向，但创建相应 issue/实施计划前应给出明确默认值或让用户确认：

- Go 服务具体 HTTP 框架、迁移工具、SQL 访问方式和仓库目录结构。
- 本地开发环境使用 Docker Compose 与否，以及 Postgres 版本。
- 网站公开内容 API 的缓存/静态生成策略与 API 不可用行为。
- 管理端与 Next.js 的部署耦合方式及认证方式。
- 文件存储后端与附件是否纳入首批询盘交付。
- 访客表单必填字段、限流阈值、垃圾询盘处理方式及隐私保留策略。
- 是否创建公开 GitHub issues；其标签、关联顺序和验收标准。
